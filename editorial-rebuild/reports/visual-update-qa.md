# 실제 작업물과 고객 자료 복원 — 브라우저 QA

검수일: 2026-10-09. 내부 production build를 Chromium에서 실행했습니다. 이 문서의 로컬 주소는 검수 대상이며 외부 미리보기 주소가 아닙니다.

## 범위와 실행

- 1440×900 데스크톱 / 390×844 모바일에서 홈, 회사 소개, 브랜드 블로그, 홈페이지형 블로그를 일반·축소 모션으로 검수: 16개 상세 상태 조합.
- 전체 12개 경로를 두 화면 크기에서 열고 끝까지 스크롤: 24개 smoke 검사.
- 마지막 서비스 hero 수정 이후 두 서비스의 첫 화면을 두 크기에서 별도 재검수. 적용된 빌드는 `main-C2hNZOG0.js`, `main-BleVIj2U.css`입니다.
- 홈의 JavaScript 비활성화 검사, 성과 수치, 가로 카드의 실제 이미지 로딩, 네이티브 휠 정·역방향과 프레임 간격을 추가 확인했습니다.
- 문의 SDK는 mock으로 대체하고 EmailJS API 요청을 차단했습니다. 실제 문의는 발송하지 않았습니다.

재현 명령은 프로젝트 `editorial-rebuild/`에서 실행합니다. production preview가 내부 4181 포트에 준비되어 있어야 합니다.

```bash
python qa/evidence-audit.py --base http://127.0.0.1:4181
python qa/evidence-supplement.py
python qa/evidence-record.py --base http://127.0.0.1:4181
```

## 원본과 사용자 동작

원본 제작 사례 7개, 고객 후기 15개, 문의 대화 8개, 총 30개가 기존 저장소 이미지와 SHA-256·치수 모두 동일했습니다. 용량 합계는 1,309,581바이트입니다. 기존 고객 자료의 진위를 외부 고객에게 새로 확인했다는 의미는 아닙니다.

- 일반 모션 홈에서 데스크톱·모바일 각각 30개 원본을 실제 뷰어로 열고 디코딩했습니다. 모든 원본이 로드되었으며 기본 큰 보기에서는 전체 이미지가 `contain`으로 표시됩니다. 원본 자체의 모자이크나 원래 잘린 영역은 그대로 유지됩니다.
- 확대는 원본 파일을 더 크게 보여주며 가로·세로 스크롤을 지원합니다. 픽셀 대 픽셀 1:1 확대라고 주장하지 않습니다. 확대 중에도 닫기 버튼이 화면에 남습니다.
- 이전·다음, 키보드 좌우 이동, Tab/Shift+Tab 초점 유지, Escape 닫기, 열었던 링크로 초점 복귀를 확인했습니다.
- 후기/문의 전환과 더 보기 후 실제 표시 수는 각각 15개와 8개입니다.
- 제작 사례 7개 썸네일, 마지막 사례 선택, 키보드 다음 선택을 확인했습니다. 모바일 실제 터치 이벤트에서 가로 스크롤은 358px 이동했습니다.
- 홈과 홈페이지형 블로그의 모바일 가로 카드 7개씩, 총 14개를 각각 탭하여 active 이미지의 디코딩과 화면 안 가시폭을 확인했습니다.
- JavaScript를 끈 홈에서도 원본 링크 7+15+8개가 모두 표시됩니다. 후기 링크를 클릭하면 원본 이미지 페이지로 정상 이동합니다.

초기 smoke 검사는 가로 화면 밖에서 지연 로딩 중인 이미지를 누락으로 분류했습니다. 검사 기준을 viewport 교차 여부로 수정하고 해당 두 페이지를 재실행했습니다. 결과의 `deferredLazyImages`는 정상 지연 로딩이며 `missingImages`는 0입니다. 이를 확인 없이 통과 처리하지 않고, 위 14개 active 카드 검사와 30개 원본 뷰어 검사로 실제 리소스 로딩을 검증했습니다.

## 표시 내용과 레이아웃

사용자가 현재도 사용한다고 확인한 기존 네 가지 수치의 라벨과 값을 그대로 표시합니다.

| 라벨 | 표시 값 |
|---|---|
| 안경 제작 사례 작성 | 5,000건+ |
| 메인 품목 재계약률 | 100% |
| 전문성 만족도 | 98% |
| 에실로 얼티밋 전국 순위 | 2위 |

두 화면 크기에서 네 값이 모두 가려짐 없이 표시되고, 장면 종료 뒤 clip-path가 제거됨을 확인했습니다. `2위`를 광고대행사 순위나 고객 매출 보장으로 바꾸지 않았습니다. QA는 표시의 정확성을 확인했으며 수치의 외부 감사를 수행하지 않았습니다.

16개 상세 조합에서 JavaScript·콘솔·HTTP 오류, 문서 가로 넘침, 검사 대상 한글 텍스트 넘침, 초기 CLS는 모두 0이었습니다. 24개 smoke 검사에서 경로 응답은 모두 200, 오류·깨진 앵커·실제 이미지 누락·가로 넘침은 0이었습니다. 보충 홈 스크롤 검사에서도 관찰한 CLS는 0이었습니다.

문의의 필수값·동의·전화번호 검증, 대기 중 중복 전송 방지, 성공 후 초기화, 실패 시 입력 보존과 결과 메시지 표시를 두 화면 크기에서 다시 확인했습니다. 기존 service/template와 payload 필드 계약을 유지했습니다.

## 모션과 성능 관찰

브랜드 장면의 시작·중간·끝 화면을 캡처하고 직접 확인했습니다. 중간 상태에서 문장이 일부 보이는 것은 reveal의 진행 상태이며, 끝 상태에서는 모두 읽힙니다. 데스크톱 네이티브 휠 정·역방향에서 브랜드 장면이 복귀하고, 제작 사례 선택은 `0 → 2 → 0`으로 바뀌었습니다. 모바일 브랜드 장면은 정적 구성으로 대체되고 제작 사례는 가로 터치로 접근합니다. 축소 모션에서도 콘텐츠와 원본 뷰어가 유지됩니다.

스크린샷·녹화 없이 별도로 측정한 각 장면 왕복 스크롤의 `requestAnimationFrame` 간격입니다.

| 화면 / 장면 | 샘플 수 | p95 | 최대 | 34ms 초과 |
|---|---:|---:|---:|---:|
| 데스크톱 브랜드 장면 | 518 | 16.8ms | 16.8ms | 0 |
| 데스크톱 제작 사례 | 464 | 16.8ms | 33.3ms | 0 |
| 모바일 에뮬레이션 브랜드 장면 | 421 | 16.7ms | 16.8ms | 0 |
| 모바일 에뮬레이션 제작 사례 | 420 | 16.8ms | 16.8ms | 0 |

이는 이 클라우드 Chromium 세션의 관찰치입니다. 실제 저사양 휴대폰 GPU, Safari, 네트워크가 느린 기기의 프레임률을 보장하지 않습니다.

## 시각 검토

새 구성은 실물 소재 이미지 → 제작 과정의 원고와 실제 작업 화면 → 큰 제작 사례 → 고객 대화 원본으로 이어집니다. 홈 첫 화면에도 실제 사례 3개의 미리보기가 보이고, 회사 소개와 두 서비스 상세에는 해당 업무를 설명하는 이미지가 배치됩니다. 텍스트만 반복되던 흐름에서 실제 업무 자료가 중심이 되었습니다.

마지막 서비스 hero 네 장, 홈·회사 소개 두 크기, 브랜드 장면 세 단계, 제작 사례 전환, 후기 목록, 원본 뷰어와 확대 화면을 직접 확인했습니다. 텍스트와 캡션의 의도치 않은 겹침이나 원본 뷰어의 잘림은 발견하지 못했습니다. 모바일 후기 목록은 여러 실제 캡처를 비교하는 썸네일이며 모든 대화 내용을 목록에서 읽을 수 있는 크기는 아닙니다. 큰 보기와 확대를 이용하면 원본을 읽을 수 있습니다.

기능 검사 통과를 디자인 승인이나 Awwwards 수준의 객관적 판정으로 간주하지 않습니다. 실제 기기·다른 브라우저 검수와 사용자의 디자인 판단은 별도입니다.

## 증거 파일과 실제 사용 지침

화면 녹화는 정지 화면을 이어 붙인 시연이 아니라 Chromium에서 실제로 발생한 프레임을 시간 간격대로 인코딩했습니다. 데스크톱은 40.93초 / 1440×900 / 3.92MB, 모바일은 37.03초 / 390×844 / 1.08MB입니다. 홈 진입, 성과, 브랜드 장면, 제작 사례 전환, 제작물 원본, 후기 확대, 문의 원본을 담았습니다. 각 영상에서 6개 시점의 프레임을 다시 추출하여 빈 화면·오류·확대와 닫기 컨트롤의 잘림 여부를 직접 확인했습니다.

- 공유용 데스크톱: `share/recordings/kotto-visual-update-desktop.mp4`
- 공유용 모바일: `share/recordings/kotto-visual-update-mobile.mp4`

- `reports/visual-update-results.json`: 원본 보존, 16개 상세 조합, 24개 smoke 결과.
