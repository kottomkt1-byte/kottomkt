## 새 서비스 문안의 사실 범위

- `scope`는 기존 서비스에 적힌 구체적인 업무를 다시 정리했다. 발행 횟수, 납기, 가격, 성과나 환불 보장은 추가하지 않았다.
- 블로그·홈페이지형 블로그·인스타그램·당근마켓·홈페이지의 `process`는 기존 5단계 흐름을 보존했다.
- 플레이스와 카페에는 원본의 명시적인 `PROCESS`가 없다. 해당 서비스에 안내된 업무를 4개의 읽기 순서로 묶었다. 새로운 계약 절차·고정 수행 순서의 증거로 사용하면 안 된다.
- FAQ는 서비스 범위의 차이와 상담에 필요한 정보를 설명하는 새 편집 문안이다. 실제 고객의 발언이나 과거 질문 통계로 표현하지 않는다.
- 고객에게 보이는 문장에서 '기존 자료에 따르면', '공개 자료로 확정할 수 없다' 같은 내부 편집 사유를 제거했다. 확정되지 않은 횟수·조건은 자연스럽게 상담 확인 항목으로 남겼다.
- 합니다체와 정확한 서비스명을 유지했다. 문의 CTA가 연결되는 행동을 설명하도록 하고 과장 형용사·상투적 대비·장식용 영문을 넣지 않았다.

현재 `script.js`와 리디자인 전 커밋의 값이 일치한다.

| 항목 | 현재 동작 |

| 전송 서비스 | EmailJS |

| 성공 | 폼 초기화 후 전송 성공 안내 |
| 실패 | 입력 내용 보존, 버튼 복원, 카카오톡 또는 이메일 대안 제공 |
| SDK 미연결 | 오류를 안내하고 카카오톡·이메일 문의로 연결 |

예산 선택지는 `50~100만원`, `100~200만원`, `200~300만원`, `300만원 이상`, `미정`이다. 상품 가격표나 최소 계약 금액이 아니다.

### 기능 검수에서 구별해야 할 한계

1. 새 Preview 도메인이 EmailJS 계정의 허용 도메인인지 확인되지 않았다. 브라우저 API 호출과 메시지 수신 여부는 다른 검증이다.
2. 폼 단위 테스트는 EmailJS 호출을 가로채 성공·실패·검증 경로를 확인해야 한다. 실제 사용자에게 메일을 보내는 전송 테스트는 수행하지 않았다.
3. 기존 개인정보 체크에는 수집·이용 목적, 보유 기간 등을 자세히 안내하는 별도 정책이 없다. 보존 의무나 기간을 임의로 작성하지 않는다.
4. 기존 전화번호 포맷은 휴대전화 3-4-4를 기준으로 한다. 지역번호 전화의 표기가 어색해질 수 있다. 이번 감사에서는 기존 로직을 변경하지 않는다.
5. root 소스에 로그인, 결제, 서버 API, 데이터베이스 저장 기능은 발견하지 못했다. 외부 EmailJS와 채널 링크를 보존한다. 소스 밖의 별도 서비스 유무를 단정하지 않는다.

## 데이터 검증

Node ESM으로 `src/content.js`를 직접 import해 7개 키와 경로, 서비스별 업무 4개·진행 4~5개·FAQ 3개 및 사업 이메일을 확인했다. 브라우저 렌더링·레이아웃·폼 QA는 구현 담당의 별도 검수 범위다.
